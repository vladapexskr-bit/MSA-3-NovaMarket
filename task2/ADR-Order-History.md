# ADR-002: Использование CQRS для просмотра истории заказов

| Поле | Значение |
|---|---|
| **Статус** | Принято |
| **Дата** | 2026-11-03 |
| **Контекст** | Требуется реализовать сценарий «Просмотр истории покупок», где пользователю нужно быстро отображать список всех заказов с их составом, статусами оплаты и доставки. Требования к отклику интерфейса — высокие. |

## 1. Контекст

Приложение построено на микросервисной архитектуре. Данные о заказе размазаны по разным сервисам:
- `Order Service` знает состав заказа и статус.
- `Payment Service` знает, оплачен ли заказ.
- `Delivery Service` знает трек-номер и способ доставки.

Если фронтенд будет делать запросы к каждому из них (или использовать API Composition), это приведет к задержкам (latency) и каскадным отказам (если упадет сервис доставки, история заказов вообще не загрузится).

## 2. Рассмотренные альтернативы

| № | Альтернатива | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| A1 | **API Composition** (API Gateway собирает данные синхронно) | Данные всегда актуальны (Strong Consistency). Просто в реализации. | Медленно из-за множественных сетевых вызовов. Высокий риск отказа (если один сервис лежит — история недоступна). | ❌ Отклонено |
| A2 | **Event Sourcing** (Хранить все изменения как поток событий) | Полный аудит. | Избыточно для простого просмотра. Сложно реализуется и запрашивается. | ❌ Отклонено |
| A3 | **CQRS (Read Model)** (Создать отдельный сервис для чтения, наполняемый событиями) | Максимальная скорость чтения. Отказоустойчивость (если упадет сервис доставки, история всё равно покажется). | Eventual Consistency (данные обновляются с задержкой в пару секунд). | ✅ **Принято** |

## 3. Решение

Мы применяем паттерн **CQRS** (Command Query Responsibility Segregation) в части разделения чтения и записи.

1. **Создаем новый контейнер `Order History Service` (Read Model).**
2. Он подписывается на все события в Kafka (`OrderCreated`, `PaymentSucceeded`, `OrderShipped`, `OrderDelivered` и т.д.).
3. При получении события он обновляет денормализованную (плоскую) таблицу в своей базе данных (`History DB`).
4. Фронтенд запрашивает историю заказов только у этого сервиса через API Gateway. Запрос возвращает уже готовый склеенный JSON за 1 сетевой вызов.

## 4. Последствия

**Положительные:**
*   **Скорость:** Чтение происходит за миллисекунды (один запрос в одну базу).
*   **Изоляция:** Падение сервисов оплаты или доставки не ломает отображение истории.
*   **Масштабируемость:** Сервис истории можно легко масштабировать, так как он только читает.

**Отрицательные:**
*   **Eventual Consistency:** Пользователь может увидеть свой заказ на пару секунд позже, чем он реально создался.
*   **Дублирование данных:** Данные о заказах теперь хранятся в двух местах (в Order Service для записи и в History Service для чтения).
